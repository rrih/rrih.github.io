# Rust migration

The personal profile, Pokémon Atlas and Pictulane remain separate products at their existing URLs. Rust owns their application behavior; WebAssembly uses the browser APIs through generated wasm-bindgen bindings. Rust `xtask` owns static generation, independent builds, asset validation and composition. Deployment only combines finished artifacts.

## Browser and library boundaries

WebAssembly uses the browser's JavaScript ABI. The retained JavaScript/TypeScript has these roles:

- Module and service-worker entrypoints, generated wasm-bindgen bindings, and adapters to the existing Three.js and web-vitals libraries.
- Vite/Workbox configuration and generated worker wiring. Atlas cache-key normalization and offline fallback decisions, and Pictulane's image-cache policy, run in Rust.
- Sharp and glTF Transform/Draco adapters for existing codecs. Pictulane's eight-line icon script resizes its existing SVG into four PNG sizes; it contains no custom drawing algorithm and is not part of the runtime or CI build.
- Playwright tests, renderer/asset verification and browser capture drivers, and Pictulane's source-investigation scripts. These remain separate from the migrated application implementation.

CSS, source data, translations, models and artwork retain their original formats. Existing Python asset-source tooling is outside this JS/TS migration. Third-party JavaScript dependencies have not been rewritten in Rust.

The legacy root worker only unregisters itself; it does not clear storage. Compatibility redirects retain their small synchronous browser redirect so query strings and fragments survive before the meta refresh. No root or `/tools/` PWA is introduced.

## Reproducible checks

Run from the repository root after installing the declared Rust target, wasm-bindgen 0.2.129, Bun, Node 22 and Chrome:

```sh
bun run dev-check
(cd atlas && bun run dev-check)
(cd tools/pictulane && npm run dev-check)
bun run compose
bun run e2e
```

Pictulane's fixture scenarios and the actual previous-release upgrade check have separate preparation steps documented in [the browser guide](../e2e/README.md). Test fixtures must never be composed for publication. Native tests also compare 10,764 SEO outputs and 1,025 numeric searches to the original implementation; renderer QA compares 55 procedural snapshots exactly.

The CI workflow verifies all three independent builds, the geometry/search oracles and the assembled browser gate before uploading the Pages artifact. Pull requests run verification but cannot deploy Pages. Public HTTP verification remains separate from local tests, Git commits and remote deployment.

## Preview server correction

Browser verification exposed a connection-reader reservation race in tiny_http
0.12.0: six accepted connections could reserve the same four idle readers,
leaving unread requests queued behind persistent keep-alive connections. The
vendored source changes that reservation condition and keeps the upstream
licenses and source hashes. A test using the actual pool starts only four of
six tasks before the fix and all six afterward; native HTTP tests also verify
idle connections and connection reuse. The root checks and CI run the pool
regression. See [the patch record](../vendor/tiny_http/LOCAL-PATCH.md).

## Compatibility constraints

- All existing localStorage, IndexedDB and model/artwork cache names and canonical cache keys are preserved.
- Generated application bindings and WASM use content-addressed pairs. Worker registration URLs and scopes remain stable; updating only one cached module must never combine incompatible releases.
- Model and artwork bytes are unchanged by this migration. Runtime asset-cache versions stay unchanged accordingly.
- Static content fingerprints and sitemap dates remain content-based. A programming-language change alone does not make the species information newer.
- The current Pictulane production provider still reports unavailable source data. Fixture success does not claim working live X acquisition.
- Browser evidence is Chrome plus emulated mobile widths and reduced-motion/offline conditions. It is not a claim of physical Safari/iOS testing or an absolute guarantee that no possible regression exists.

Release verification remains incomplete until the pending checks above have a recorded outcome.
